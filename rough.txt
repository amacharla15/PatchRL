# Rebuilding the LLM Kernel Optimization + Post-Training Stack

## KernelBench → KernelGYM → veRL → Dr.Kernel → Our Own Extension

### Goal

The purpose of this project is **not initially to invent a new kernel-generation method**.

The goal is to rebuild and understand, from first principles, the modern stack used to train language models to generate and optimize GPU kernels.

We will progress through:

```text
PyTorch workload
      ↓
Kernel generation
      ↓
Correctness + performance evaluation
      ↓
Scalable GPU evaluation environment
      ↓
Agentic multi-turn optimization
      ↓
SFT
      ↓
RL with verifiable GPU rewards
      ↓
Distributed RL infrastructure
      ↓
Reward-hacking defenses
      ↓
Test-time scaling
      ↓
Our own extension
```

The major systems studied are:

```text
KernelBench
    ↓
KernelGYM
    ↓
veRL
    ↓
Dr.Kernel
```

Rather than merely cloning each repository and running provided scripts, we will first implement **small versions ourselves**.

The guiding principle is:

> Encounter the problem first. Then understand why the production system contains the machinery it does.

---

By the end, we should understand how the following subjects connect.

### GPU / kernel systems

* Triton

* kernel fusion
* launch overhead

### LLM inference

* vLLM / SGLang

* inference/training resource contention

### Agentic AI

* model → action → environment → observation
* tool use

* context management
* test-time search
* retry policies
* selecting the best candidate

### Post-training

* supervised fine-tuning
* reinforcement learning
* RLVR
* GRPO
* RLOO
* TRLOO
* reward design
* reward shaping

### Distributed systems

* workers

* training/inference separation

The important point is that these are **not five separate learning tracks**.

They all become necessary because of one problem:

> How do we teach a model to repeatedly produce correct GPU kernels that are faster than an existing implementation?

# 2. The Big Picture

## Layer 1 — KernelBench

Question:

> Can an LLM replace a PyTorch implementation with a correct and faster GPU kernel?

Basic loop:

```text
PyTorch reference
       ↓
Prompt LLM
       ↓
Generated Triton/CUDA
       ↓
Compile
       ↓
Correctness check
       ↓
Benchmark
       ↓
Speedup score
```

This teaches **evaluation**.

---

## Layer 2 — KernelGYM

KernelBench evaluates kernels.

Now imagine doing that tens or hundreds of thousands of times during RL.

We need:

```text
model rollouts
      ↓
evaluation API
      ↓
task queue
      ↓
GPU workers
      ↓
isolated compilation/execution
      ↓
correctness
      ↓
benchmark
      ↓
profiling
      ↓
reward
```

This teaches **environment + distributed systems**.

---

## Layer 3 — veRL

KernelGYM gives us rewards.

But someone still has to:

```text
generate rollouts
compute advantages
manage policy/reference models
perform training
synchronize weights
allocate GPUs
run distributed workers
```

That is the role of an RL training framework such as **veRL**.

This teaches **RL infrastructure**.

We will not rebuild veRL.

We will understand enough of it to know what happens between:

```text
prompt
  ↓
rollouts
  ↓
rewards
  ↓
advantages
  ↓
gradient update
```

---

## Layer 4 — Dr.Kernel

Dr.Kernel combines the pieces.

Conceptually:

```text
Qwen base model
      ↓
SFT cold start
      ↓
multi-turn kernel generation
      ↓
KernelGYM feedback
      ↓
RL
      ↓
specialized kernel model
```

Its training recipe introduces techniques including:

```text

Mismatch correction
Dual-clip ratio clipping
Profiling Rewards
Profiling Rejection Sampling
```

This teaches **actual post-training**.

## Architecture

```text

                │
            HTTP request
                │
                ▼

        evaluation server

                │
             task queue
                │

        ▼       ▼       ▼

       │       │       │

        └───────┼───────┘
```

Do not prematurely distribute across ten machines.

```text

```


```json

  "compiled": true,
  "correct": true,
  "latency_us": 17.4,
  "baseline_us": 21.8,
  "speedup": 1.25,
  "reward": 0.72
}
```

# 13. Milestone 10 — GRPO / RLOO / TRLOO

Only now should these acronyms matter.

They are different answers to:

> Given sampled outputs and rewards, how should we estimate which behavior deserves to be reinforced?

Do not think:

```text
PPO → GRPO → RLOO → TRLOO
```

as sequential upgrades.

They are alternative methods.

---

## GRPO

Generate a group:

```text
A
B
C
D
```

compare rewards within the group.

Higher-performing responses are reinforced relative to lower-performing ones.

---

## RLOO

Uses leave-one-out reward baselines.

Again, same broad problem:

```text
How good was this sample relative to an appropriate baseline?
```

---

## TRLOO

Dr.Kernel's multi-turn variant.

The important problem is:

```text
turn 1
  ↓
turn 2
  ↓
turn 3
```

Rewards and decisions are related across a trajectory.

Naive group-relative calculations can create biased signals when the same trajectory influences its own baseline.

TRLOO addresses that multi-turn setting.

We should first understand **the problem**, then study the equation.

# 19. The Extension Is Deliberately Undecided

After replication, ask:

### Evaluation problems

```text
Can the evaluator still be gamed?
Are timings noisy?
Are correctness checks insufficient?
```

### Systems problems

```text
Is compilation the bottleneck?
Are GPU workers underutilized?
Is queue scheduling poor?
Does reward evaluation dominate RL wall-clock?
```

### RL problems

```text
Are rewards too sparse?
Does TRLOO materially help?
Does the model overfit visible tasks?
Does RL improve beyond SFT?
```

### Agent problems

```text
Does context become bloated?
Does the model repeat failed strategies?
Can retrieved past optimizations help?
```

### Kernel problems

```text
Does optimization generalize across shapes?
Across GPUs?
Across Triton versions?
Across NVIDIA generations?
```

Whichever problem hurts the most becomes our real extension.

Possible directions:

```text
GPU regression CI
cross-hardware optimization
automatic kernel repair
compiler regression diagnosis
better context memory for kernel agents
faster verifier infrastructure
better reward-hacking defenses
kernel optimization distillation
specialized small kernel model
```

But we should **earn the right to choose this after replication**.
